# RFC-03: Migrating Carousel Agent v2 → "Instagram Agent" onto `agent-engine`

**Depends on:** RFC-01 (engine core), RFC-02 (migration recipe, §2)
**Source material (read directly this session):** `karos-agents/products/building/carousel-agent-v2/{README.md,SKILL.md,setup/SKILL.md,manager/SKILL.md}`, `karosCMO/docs/carousel-agent-portal.md`, `karosCMO/scripts/{register-carousel-agent-v2.ts,set-carousel-agent-models.ts}`
**Status of the source product:** registered in Firestore (`customAgents`), **`enabled: false`, `source.status: "blocked"`** — in build, no pilot run has ever produced a carousel for a real client. This changes the migration calculus: see §1.

**Naming:** per your instruction, this agent is renamed **"Instagram Agent"** in `agent-engine` and in the portal-facing name/key going forward. The underlying product folder (`carousel-agent-v2`) and its legacy predecessor (`products/live/instagram-agent/`, a *different*, older product with its own six credentials — do not confuse the two) keep their existing names in `karos-agents`; only the new engine's agent and its portal display name change.

---

## 1. Why this is a different kind of migration than X

X (RFC-02 §3) is **live** — real client traffic runs through the legacy skill today, so its migration has to preserve a working system while replacing its runtime underneath. Carousel/Instagram is the opposite case: it is **registered but disabled, with zero pilot runs**. Nobody is currently depending on its current execution path. That is a genuine advantage — use it:

**Recommendation: build the Instagram Agent as the first agent implemented natively on `agent-engine` from day one, rather than a migration-from-a-working-legacy-path.** There is no legacy behavior to preserve compatibility with, no shadow-run comparison needed against a live baseline, and no risk of disrupting client-facing traffic. The "migration" here is really: take the already-excellent, already-debugged skill design (real defects were found and fixed in the v1→v2 rebuild — see §2) and implement it as the first clean `BaseAgent`/workflow pair, skipping the "port legacy, then harden" two-step X needed.

One caveat: the `customAgents` document already exists (id TBD, key `karos-carousel-agent` per `CAROUSEL_RUNNER_KEY` in `karosCMO/src/lib/custom-agent-launch.ts`) with two sub-agent documents (`karos-carousel-setup`, `karos-carousel-manager`) nested under it via `parentKey`. Renaming to "Instagram Agent" means either updating that document's `name`/`clientBlurb` in place, or retiring it and registering a new one under `agent-engine`'s own portal-integration path (RFC-01 §7) — this is a real choice, not a detail; see §6.

## 2. What the v1→v2 rebuild already fixed — preserve every one of these, don't reintroduce them

The `carousel-agent-v2` README documents three **measured** defects in the legacy product, each with real numbers. These are exactly the class of bug RFC-01's architecture (§4's layer invariant, §9.1's tool rules) exists to make structurally impossible — treat them as acceptance criteria for the new implementation, not just history:

1. **Context bloat (measured 48,912 words before anything was produced).** The legacy build read an 8,120-word master file plus an 8,880-word feedback ledger *in full, every build*, growing unbounded. Fix already designed: setup reads the ledger **exactly once**, compiles a small `02-style-config.json` (target under 1,200 words), and the runner is **forbidden** from opening any of the nineteen original sources. **In `agent-engine` terms: this is exactly RFC-01 §4.5's "retrieve, don't load whole" memory rule, and the "forbidden list" becomes `allowedTools`/context scoping enforced by the runner step's config, not a written rule a model is asked to obey.**
2. **A rogue rendering path.** The legacy runs each wrote their own renderer, and the worst instance hardcoded an absolute path into one engineer's local git worktree — unreproducible by anyone else, and it bypassed every quality gate because the gates assumed the product's own engine had rendered. Fix already designed: the agent writes only `slides-data.json` (a typed, repo-relative data contract); **one static renderer serves every client** (`assets/engine/render.mjs`); absolute paths are refused in code with a tooling exit. **In `agent-engine` terms: this is precisely RFC-01's rendering step should be a deterministic `karos-publish`-family tool (§9.2), never something an agent step writes its own code for — and the "refuse absolute paths, exit tooling-not-content" behavior maps exactly onto RFC-01 §6's `tooling_error` category.**
3. **The ledger illusion.** The legacy product had two dedup mechanisms; measured across all four legacy clients, the topic-catalogue flips worked 4 of 4 while the file its own skill called "the hard dedup gate" existed for only 1 of 4 clients — three clients were silently deduplicating on a mechanism nobody knew was inactive. Fix already designed: **the topic catalogue is the single, sole dedup authority**, claimed *before* the expensive work runs. **This is RFC-01's `karos-topics` server (§9.2) exactly as specified — reserve-before-work, one authority, no shadow mechanism.**

## 3. The real run protocol (from `SKILL.md`, read in full) — nine steps, already close to RFC-01's shape

| # | Step (real) | Tier | Tools (RFC-01 §9.2 mapping) | Notes / resume semantics |
|---|---|---|---|---|
| 01 | Open the run, take the steer | code | `client.getConfig` (readiness check), a new `carousel.claimRunNumber`-style tool | Hard gate: setup must show `COMPLETE — ready` or `HALT`. Claims the next post number from existing folder/run count. A client-supplied "steer" (from `next-request.md` today) may pick lane/subject but never relax a lock — model this as an optional run-input field, not free text injected mid-run. |
| 02 | Freeze the small files | code | `client.getConfig`, `client.getBrand` | Pin style-config + brand tokens before reading — exact match to RFC-01's "pin inputs before reading" rule (RFC-02 §3's run-protocol notes for X apply identically here). Parse-check all three; a bad version or absolute path is a `HALT`, not a silent default. |
| 03 | Claim the topic | code | `topics.reserve`, `topics.topUp` | **The only dedup gate — by design, per §2.3 above.** Below a floor of 5 unused rows, invent + append new candidates with evidence before picking (matches RFC-01 §9.2's `topics.topUp`). Claim before any paid work runs. |
| 04 | Research the subject | agent, bounded | `research.pull` | Verbatim payload saved before parsing (RFC-01 §9.1 rule, already correctly designed here). Every fact that will reach a slide needs a source + date — no drafting step may search afterward. |
| 05 | Write the copy | agent, bounded (pinned tier — this is the creative judgment call, per RFC-01 §5.4) | craft skill (voice/style) | Six to eight slides, one idea each. Every claim traces to a step-04 source — this trace is what the next step's gate checks. |
| 06 | Source and vet one picture per slide | agent, bounded, with internet | a new `carousel.findImage`-style tool | **Real judgment, not a rubber stamp**: fetch, open, and *look at* the image — does it show what the slide claims, is it rights-usable, watermark-free, right era. A slide with no viable image **holds the whole post** (`HELD`) rather than shipping a placeholder — this is exactly RFC-02's `held` outcome (see RFC-02 §3's reconciliation note), not a `failed`. |
| 07 | Emit the data | code (rule) | — | Writes the single data contract (`slides-data.json`) the renderer consumes — see the schema in `SKILL.md` step 07, directly portable to a Zod schema. Self-checks before rendering: every claim traces to a source, every config rule with `check: "copy"` passes, slide count matches step 06. A fail here is `RETURN: 05` (revise), capped at two returns before the post is `HELD`. |
| 08 | Render | code (deterministic) | `karos-publish`-family tool wrapping `render.mjs` | **Three-way exit code, not two** — this is a real, already-correct instance of RFC-01 §6's taxonomy: `0` success, `1` = `content_fail` (a named slide failed, return to drafting), `2` = `tooling_error` (bad path, missing template, Chromium/Playwright absent — **never** recorded as "no images for this post"). Needs `playwright` — **not currently installed in the repo** (see §5, a real blocker). |
| 09 | Deliver and log | code | `ledger.writeDeliverable`, `ledger.appendEvent`, `topics.commit` (confirm survival) | Client folder written only for a fully-successful post; row-count-matches-slide-count checks before any ledger append (exactly RFC-01 §9.1's idempotent-write discipline); re-confirms the step-03 topic claim survived a concurrent run before finishing. |

**Setup (runs once per client)** and **Manager (monthly pass, currently a stub — "shape fixed, judgment steps unwritten")** exist as separate skills, matching RFC-02's setup-workflow / manager-workflow split exactly. The manager being an intentional stub is useful: **build its `agent-engine` workflow shape now, with the two real jobs already specified** (append fresh topics to the catalogue; *propose* — never auto-apply — style-config changes, since "a look that changes underneath a client mid-month is a grid that stops matching itself") even though the judgment logic inside can stay minimal until real runs exist to learn from.

## 4. Tools needed — mostly shared, two genuinely new

Per RFC-02 §2 step 5 ("reuse the shared registry, add only what's genuinely new"):

- **Reuse as-is:** `client.*`, `research.pull`, `topics.*`, `ledger.*` (RFC-01 §9.2).
- **New, agent-specific:**
  - `carousel.findImage` (or generalize as `media.findImage` if other future agents need image sourcing) — fetch + fetch-and-inspect an image candidate, returning a typed verdict (`found` with license/URL, or `held` with reason) per slide. This is real judgment (a vision-capable model call), not a deterministic tool — model it as a bounded `BaseAgent` step (tier: portable — extraction/verification work, not brand-voice creative judgment) that *calls* a deterministic `media.fetchImage` tool for the actual HTTP fetch.
  - A `karos-publish` server entry wrapping the existing `render.mjs` renderer (or its eventual successor) as a typed tool: input = the `slides-data.json` shape, output = the three-way verdict from step 08 above. **Do not rewrite the renderer logic** — it's already correct (path-guarded, self-testing, deterministic); wrap it, don't replace it.

## 5. Known gaps to resolve before or during migration (not invented — copied from the source README's own "Known gaps" section)

- **`playwright` is not installed in the `karos-agents` repo.** The render step will exit `2` (tooling failure) until this is fixed. Since the render tool now lives in `agent-engine` (a different repo, per RFC-01 §1.1), this is actually simpler to resolve than it was in-place — just ensure `agent-engine`'s own `karos-publish` package has `playwright` as a real dependency with its browser binaries available in whatever container runs it (Cloud Run needs the Playwright browser layer baked into the image).
- **No pilot run exists anywhere.** There is no reference output to validate against. **This means the eval golden-run (RFC-01 §12) for this agent has to be produced fresh** — plan for a supervised first run (with Albert or whoever owns Instagram/carousel product judgment) specifically to produce the golden run, rather than assuming one can be mined from history the way X's migration might eventually be able to.
- **The manager is unimplemented judgment.** Don't invent monthly-review logic from scratch; build the workflow shape (§3) and stub the judgment step, matching the source skill's own honest "stub, mode: stub" status.

## 6. Portal integration — a real open decision, not a detail

The existing `customAgents` documents for this product (`karos-carousel-agent` runner + two `parentKey`-nested sub-agents `karos-carousel-setup`/`karos-carousel-manager`) are a genuinely good pattern worth learning from for RFC-01 §7: **the parent/child grouping is exactly how the portal shows "one product, several internal steps" as a single card**, and it's a cleaner precedent than anything in the `dynamic-agent-*` system for representing a setup+runner+manager triad as one product. Two real choices:

1. **Rename in place.** Update the existing three `customAgents` documents' `name`/`description`/`clientBlurb` fields to "Instagram Agent" and point `entrySkillDir`/whatever config `agent-engine` needs at the new engine instead of the legacy skill path, keeping the same Firestore document ids (and therefore the same grant/roster history, if any exists yet — likely none, since it's never been enabled).
2. **Register fresh under `agent-engine`'s own integration path**, and deprecate (don't delete) the old documents, per the existing script's own stated policy of being purely additive and never deleting the product it's described as replacing.

**Recommendation: option 1 (rename in place).** Since nothing has ever been enabled or granted, there's no live state to lose, and reusing the same document avoids leaving an orphaned, confusing "Carousel Agent" entry sitting disabled in the admin library forever. Confirm with whoever owns the `customAgents` admin library UI before executing either way — this script-driven registration pattern (`register-carousel-agent-v2.ts`) also demonstrates the **better** prompt-storage pattern flagged in RFC-01 §16.1 (it reads instructions from a git-tracked Markdown doc with fenced code blocks per agent, rather than an inline string like X's registration script) — worth generalizing this exact pattern (doc-with-fenced-blocks → Firestore) into `agent-engine`'s own prompt-store tooling rather than inventing something new.

## 7. Definition of done

Per RFC-02 §7, plus one addition specific to this agent: since there is no legacy production behavior, "no regression vs. legacy" is replaced by **"the supervised first pilot run, reviewed by a human, is accepted as the golden run"** — this agent's migration is done when that pilot run exists, passes its evals, and the renamed "Instagram Agent" is enabled for at least one real client.
