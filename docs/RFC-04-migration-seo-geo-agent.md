# RFC-04: Migrating SEO & GEO (`a3` / `karos-seo-geo`) onto `agent-engine`

**Depends on:** RFC-01 (engine core), RFC-02 (migration recipe, §2)
**Source material (read directly this session):** `karos-agents/products/onboarding/step-02-seo-geo/{README.md,AGENT.md,SKILL.md}`, `karos-agents/catalog/products-catalog.json` (product `a3`), `karosCMO/scripts/refresh-seo-geo-locally.ts`
**Status of the source product:** "v1, consolidated to ONE skill 2026-07-06. Product logic proven end to end on 2 real clients... Live automation and first-party Google data are post-v1." **Not currently registered as a `customAgents` or dynamic-agent document at all** — it runs as an in-process TypeScript library call (`runSeoGeoResearch`, `src/lib/intel/seo-geo.ts`), invoked either as a sub-step of the onboarding pipeline or standalone via an admin script. This is a fundamentally different starting point than X or Instagram — see §1.

---

## 1. This migration is an extraction, not a rewrite — and it's the most consequential one of the three

Two things distinguish this migration from X's and Instagram's:

1. **It doesn't currently have a job/run record at all in the portal's normal sense.** `runSeoGeoResearch` is called directly from server-side code (`runOnboardPipeline` at onboarding, or an admin "Regenerate"/refresh action later), writes its result via `upsertClientSeoGeo` directly into Firestore, and has none of the machinery (job queue entry, `customAgents`/dynamic-agent document, portal-visible run history) every other agent in this document set has. Migrating it onto `agent-engine` is therefore **the first time this product gets a real, inspectable run history** — a genuine capability upgrade, not just an engine swap.
2. **The pipeline itself is unusually rigorous and already deterministic by design** — this is the single most important fact for this migration. Multiple phases explicitly forbid model creativity ("No creativity is permitted in this phase" — Phase 4 scoring), enforce frozen, hashed inputs for reproducibility, and have **live, named, blocking decisions gated on specific people** (see §4). **The job of this migration is almost entirely to preserve this exactly, not to improve it** — the biggest risk here is an engineer "helpfully" turning a deterministic scoring function into an LLM call because it's being ported into an agent framework. Don't. RFC-01's own architecture already anticipates this: §4.2's "mechanical" tier (zero LLM invocation, pure TypeScript functions) exists precisely for phases like this one.

## 2. The real phase map (from `SKILL.md`, read in full) — map to workflow steps, not agent judgment, except where marked

| Phase | What | Tier (per RFC-01 §4.2) | Why |
|---|---|---|---|
| 0 | Context intake (brand aliases, competitor roster, category vocabulary) | code | Pure extraction from existing profile docs — no live research yet. |
| 1 | Prompt set + roster, frozen | **agent, bounded** (drafting 20–35 prompts) + code (freeze/hash) | Drafting is genuine judgment (never hardcoded, never reused across clients); the freeze step (hashing prompts/roster/gazetteer/engine-list) is pure code and must be exact — these hashes are the reproducibility spine for the whole run. **Requires a human/client confirmation gate** (`gate.promptSetApproval`-style) before freezing — this is currently a sign-off file in the lab and an approval screen on the platform; make it a first-class `Gate` (RFC-01 §8.3) either way. |
| 2 | Crawl + technical SEO measurement | code (deterministic crawl + measurement) with **agent, bounded** sub-steps for the four parallel sub-agents (technical infra, on-page, performance/CWV, keyword+content gaps) described in `process/phase-1-technical-seo.md` | The sub-agents do real analysis/judgment (hence "bounded agent," not pure code) but every finding needs a confidence label (CONFIRMED/LIKELY/HYPOTHESIS) and evidence — model each as a bounded `BaseAgent` step with a strict output schema enforcing that shape, run as a `fanout` (RFC-01 §5.5/§8.2) since the four sub-agents are independent. |
| 3 | AI-visibility capture (5 fixed engines: chatgpt, perplexity, gemini, claude, copilot) | code, calling external APIs directly — **not an agent step**, despite calling LLM APIs | This is the phase most at risk of being mis-modeled as "agent work" because it calls Perplexity/OpenAI/Gemini/Anthropic. It isn't — it's a deterministic capture-and-parse pipeline ("no LLM judges any number... parse deterministically"). Model every engine call as a `research.pull`-style **tool**, not a `BaseAgent` step. The Anthropic/Claude column call is explicitly "Haiku-class capture calls, never the report model" — i.e. even where a model is invoked, it's functioning as a data source being measured, not as a reasoning step in the workflow. |
| 4 | Deterministic scoring | **code, pure function, zero LLM calls** | Explicitly "no creativity is permitted." Port the scoring config (`seo-geo-scoring-config.json`) and its normalization primitives (`boolean`, `count_with_target`, `ratio_clamp`, `percentage`, `lower_is_better_stepped`) as-is into a typed, unit-tested pure function in `agent-engine`. This is the single easiest phase to get very wrong by "agentifying" it, and the single most important one to get exactly right, since it's the client-facing grade. |
| 5 | Connector overlay (works unconnected, upgrades when Google is connected) | code | A source-ladder lookup (`first_party_google > measured_ai_capture > research_estimate > UNAVAILABLE`), not judgment. Every accuracy upgrade is a **logged drift event**, never a silent change — port this logging behavior into RFC-01's telemetry (§11), it's directly compatible. |
| 6 | Recommendations (product-linked or honestly advisory) | code (the firing/routing logic is a deterministic rule: "a rec fires when `min(norm across its weighted inputs) < 1.0`") | Deterministic rule evaluation against `seo-geo-rec-catalog.json` and `seo-geo-routing-config.json`. No agent judgment in the firing decision itself. |
| 7 | **GATE**, then fix generation | `gate.*` (RFC-01 §8.3) then **agent, bounded** per fix type | The gate here is load-bearing and explicit in the source skill itself: "nothing is generated or shipped past this point without sign-off." Fix generation (rewritten titles/meta, FAQ blocks, schema, outreach packs, entity kits) is real creative/technical output — bounded agent steps, one per fix type, fanned out. |
| 8 | ONE merged report | code (assembly) + **agent, bounded** for the narrative sections (executive summary) | The report structure itself (scores, coverage %, ranking grid, findings) assembles from Phase 0–7's typed outputs; only the prose narrative wrapping needs a drafting step, and even that should be tightly constrained against the underlying numbers (a `gate.numbersSourced`-style check, RFC-01 §9.2, is directly applicable here — arguably more important here than anywhere else in the whole agent portfolio, given the "grade = measured data only" rule in §4). |

## 3. Two run modes, one pipeline — model as two workflow entry points sharing the phase implementation

Per the catalog and `README.md`: this runs **twice over a client's life** — once as onboarding step 2 (chained automatically after `step-01-onboard`, "baseline" mode) and monthly as the `a3` recurring-optimization SKU. Build one shared workflow (`seoGeoRun(ctx: {mode: "baseline" | "recurring", ...})`) implementing the phase map in §2, with the only mode-specific difference being **Phase 1's prompt-set handling**: baseline mode drafts a fresh prompt set; recurring mode reuses the frozen prompt set from the prior run "for trend comparability" (changing it is itself a logged drift event, never silent, per the source skill). This maps cleanly onto RFC-01's workflow primitives — a single workflow definition parameterized by `runKind`, exactly as RFC-01 §5.1's `AgentContext.runKind` already anticipates (`"setup" | "recurring" | ...`).

## 4. Gated, blocking decisions to preserve exactly — do not resolve these during migration

The source material names several **specific, currently-open, human-owned decisions**. A migration must carry these forward as explicit blockers in the new system, not silently pick a default:

- **`config/seo-geo-connectors-config-edits.txt`** — an additive edit plan for the scoring/capture/metrics configs, explicitly "GATED on Daniel's determinism sign-off, deliberately NOT applied." The three live configs reference it by name. **Do not apply it, rename it, or fold its contents into the migrated configs without that sign-off** — port it as a separate, clearly-labeled pending-change file, not merged in.
- **N vs N_e visibility denominator** — described as a "BLOCKING scoring-model decision for Daniel." The current skill freezes both N and N_e per capture cell specifically so either definition reproduces from the same blob once decided. Preserve this dual-freeze behavior in the migrated capture tool (§2 Phase 3) exactly — don't pick one prematurely because a typed schema "should" have one field.
- **Classic-Google ranking data** is blocked on Search Console verification (`GSC_SERVICE_ACCOUNT_KEY`/`GSC_SITE_URL` unset) — this is an infrastructure/credentials gap, not a design gap. Track it as a known-unavailable connector in the migrated system's `karos-research` server (RFC-01 §9.2), surfaced honestly as `UNAVAILABLE` per the source skill's own rule ("terminal UNAVAILABLE, never a fabricated zero") rather than silently omitted.
- **`geo_score_model` (geo-score-v3) per-engine weights** are explicitly "PROPOSED pending Ines." Carry the pending status forward; don't treat it as final just because it's the only implementation available to port.

**General rule for this migration specifically:** where the source skill says a number is `pending`, `UNAVAILABLE`, or gated on a named person, the migrated `agent-engine` implementation must represent that exact state (as a typed value, not an omission) — this system's entire credibility rests on "grade = measured data only," and a migration that quietly fills in a gap to make a schema simpler would be a real, client-facing regression in trustworthiness, not just a technical shortcut.

## 5. Tools needed — this agent has by far the largest connector surface of any agent in this document set

Per the catalog's `needs_credentials` list: `AHREFS_API_KEY`, `CLAUDE_API_KEY`, `CMS_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_SEARCH_CONSOLE_TOKEN`, `PERPLEXITY_API_KEY`, `SERPAPI_API_KEY`, `SEARCHAPI_API_KEY`, `OPENAI_API_KEY`. This is the strongest real-world forcing function in the whole migration effort for building out `karos-research` (RFC-01 §9.2) properly — recommend this agent's migration be the one that fully generalizes the research tool server's multi-provider capture pattern (raw payload + parsed result + frozen capture-tier label, per §2 Phase 3), since every future research-heavy agent benefits from whatever's built here. Concretely, model each of the five AI-visibility engines (chatgpt, perplexity, gemini, claude, copilot) as one `research.pull` invocation with a `provider` argument, sharing one typed response shape (`{raw_blob_ref, raw_sha256, answer_text, citations[], capture_tier}` from the source skill, directly portable to a Zod schema) — not five bespoke tools.

New, agent-specific tools beyond the shared registry:
- `seoGeo.crawl` — the technical crawl/measurement capture (Phase 2).
- `seoGeo.score` — the pure deterministic scoring function (Phase 4). **This one is worth its own dedicated, extremely thorough unit test suite** (RFC-01 §12's deterministic-assertion tier) given the "no creativity" rule — arguably the single highest-value eval target in this entire program, since a scoring regression here is a wrong client-facing grade, not just a worse draft.
- `seoGeo.recommend` — the rule-based rec-firing/routing logic (Phase 6).

## 6. Portal integration — genuinely new, not a rename

Unlike X and Instagram, there is no existing `customAgents`/dynamic-agent document to rename or reconcile. This migration includes, as a first-class deliverable, **registering SEO & GEO as a real portal-visible agent for the first time** — following the Instagram Agent's registration pattern (RFC-03 §6: instructions read from a git-tracked doc, not inlined) rather than X's (inline string). Given the size and structural complexity of this product (nine config files, eight phases, cross-references to `docs/one-pagers/seo-geo-handoff.html` for the sales-facing summary), recommend representing it in the Dynamic Agent Studio model (RFC-01 §7) rather than the older `customAgents` shape, since the phase map (§2 above) is naturally expressed as a sequential `DynamicAgentStepDef[]` list once each phase's code/agent boundary is settled — and the Studio's cost-per-step reshape (RFC-01 §7.1, already validated in the real codebase) is especially valuable here given how many distinct external API calls one run makes.

## 7. Definition of done

Per RFC-02 §7, with two additions specific to this agent: (1) the deterministic scoring function (`seoGeo.score`) has a unit test suite that reproduces the exact scores from at least the two real clients the source skill was already proven against ("2 real clients, two industries, two languages" per the README) — this is the closest thing to a golden run this agent has, and matching it exactly is non-negotiable, not just "close enough"; (2) every gated/pending decision from §4 is represented as an explicit, visible pending state in the migrated system, confirmed against Daniel/Ines before this migration is called complete, not silently resolved by whoever implements it.
