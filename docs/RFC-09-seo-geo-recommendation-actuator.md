# RFC-09: The SEO & GEO Recommendation Actuator ("Phase 7")

**Depends on:** RFC-01 (engine core), RFC-04 (SEO & GEO migration — this hangs off its Phase 4+ scoring output)
**Source material (read directly this session):** `karosCMO/src/lib/seo-geo.ts` (the real, current `VisibilityGap`/`Recommendation`/`ActionKind`/`FixAction` types and their comments, ~100KB, read in targeted sections), `karosCMO/src/lib/{copilot-context.ts,copilot-tool-access.ts}`, `karosCMO/src/lib/types.ts` (`ClientIntegration`), plus the karos-agents reference doc `products/onboarding/step-02-seo-geo/docs/SEO-GEO-RECOMMENDATION-AUTOMATION.md` and `process/fix-recipes.md` — treated as design reference only, per §2.
**Framing note:** the user asked, informed by a ChatGPT/Gemini brainstorm, for a system that splits every SEO/GEO finding into "we can just do this for you" versus "here's exactly what to do and an assistant to help." **That system already exists in outline in the current codebase — this RFC specs the one piece of it that is not yet built.**

---

## 1. This is not a new feature to design from scratch — it is "Phase 7," already named and already waiting for an implementation

`seo-geo.ts` already has a real, shipping (or near-shipping) client-facing recommendation system, evolved through a real QA process (its comments cite specific findings: QA F9, F16, F22, F81, F89, "CD-J1", "dev-handoff §3a/§3b/§4"). It is considerably more nuanced than a two-way split. The actual `ActionKind` is four-way:

```ts
export type ActionKind = "one_click" | "review_approve" | "connect" | "guided_manual";
```

- **`one_click`** — the fix is both **agent-direct** (we generate it) and in `MACHINE_APPLIABLE` (`meta_title`, `meta_description`, `canonical`, `sitemap`, `image_alt`, `schema`, `og_image`, `indexing`) — but see §3: even this is not "silently goes live."
- **`review_approve`** — agent-direct, but not machine-appliable — a human reviews the generated fix before it ships.
- **`connect`** — routes through an **existing Karos product** that needs a connected credential first (the code's own example: Google Search Console).
- **`guided_manual`** — **advisory**: the agent drafts a kit, a human (Karos or the client) ships it. This is exactly the user's "bucket 2."

The client already sees this: `buildRecommendations()` derives a `Recommendation[]` from the internal `VisibilityGap[]`, with plain-English copy (`REC_COPY`, one entry per check id, test-pinned for coverage), and `approveSeoGeoRecommendation()` already lets a client or staff member approve a `recId` into `approvedRecIds[]`. **What does not exist yet is anything that reads an approved `recId` and actually does the fix.** The field is right there, waiting: `artifactRef?: string | null` — "Generated-fix artifact path — **null until the Phase 7 actuator runs**." This RFC is the spec for Phase 7.

## 2. A richer, parallel design already exists — for infrastructure this product does not run on

`karos-agents/products/onboarding/step-02-seo-geo/docs/SEO-GEO-RECOMMENDATION-AUTOMATION.md` ("status: spec for build," 2026-06-24) describes a considerably more ambitious version of this exact idea: a 75-`rec_id` catalog, three delivery classes (agent-direct/existing-product/new-product), a deterministic priority/dedup engine, a capacity-capped drip calendar, and **six named safety gates — including a documented CRITICAL finding that its own designed `seo-fix-agent` would write live to a client's WordPress with no approval check unless gate 4 is built.**

**This document describes different infrastructure than the one this session has been building agent-engine against.** It names `research_runs`, `rec_actions`, `approval_queue`, and Postgres/Supabase-specific mechanics (row-level security, "service-role write, anon SELECT") and named edge functions (`recurring-agent-runner`, `ceo-agent`, `seo-fix-agent`, `commit-deliverable-to-git`) — **none of which exist anywhere in the current `karosCMO/src/lib` tree** (checked directly this session, full recursive listing, zero hits). `seo-geo.ts`'s own comment confirms the split explicitly: `productRef` is "**null in the SaaS (no rec-catalog here)**" — the current product ("the SaaS") deliberately does not carry the 75-rec catalog or its routing table today. This is the same shape of finding as RFC-07 §2 (Landing Builder vs. `website-redesign`): **two real, well-thought-out designs for the same problem, on different infrastructure, never reconciled.** Do not silently merge them. Recommendation: **use the karos-agents doc as a design reference** for the ideas worth keeping — the priority formula, the dedup-by-scope-hash logic, the capacity-capped drip calendar, and above all the **safety-gate discipline and its own documented near-miss** — but implement Phase 7 against the real, current `seo-geo.ts` types and Firestore-backed infra, not the Supabase-shaped one. Whether the fuller 75-rec catalog is ever adopted into the SaaS product is a real product decision for whoever owns a3, not something this migration should decide by default.

## 3. The one rule that must not be violated: nothing here is "silently goes live," including `one_click`

Every other agent migrated in this set defaults to draft-then-approve: Reputation Agent starts and stays at `approve-all`; Branded Shorts and Landing Builder both route every early output through human QA before anything ships; the karos-agents actuator doc's own Gate 4 exists specifically because an unguarded auto-write was found in its own design. `seo-geo.ts`'s own `ownerFor()` already agrees: **`one_click`'s owner label is the same as `review_approve`'s — "Karos SEO & GEO · we draft, you approve."** The product's own copy already treats "one click" as "one click to approve a fix we already prepared," not "one click and it is live." **Phase 7 must preserve this literally**: every `one_click`/`review_approve` fix produces a **previewable diff** before any write, and the live write is a separate, explicit step gated on (a) the `recId` being in `approvedRecIds`, and (b) — matching the karos-agents doc's Finding 4 exactly — a resolved `deliverable`/approval record, not just the presence of the id in an array. Treat the `approvedRecIds` check as necessary, never sufficient.

## 4. Architecture: three actuator paths off one shared trigger

The trigger is the same for all three: a client or staff member calls `approveSeoGeoRecommendation(recId)`. What happens next depends on the gap's `delivery`/`fixAction`, resolved server-side — **never** by trusting a client-supplied `actionKind` (RFC-01 §9.1's rule: tenant/scope from run context, never a model or client argument).

| Path | When | What it does |
|---|---|---|
| **A — Direct CMS write** (`one_click`, `review_approve`) | `fixAction` is one of the eight machine-appliable actions AND the client has a connected, working CMS credential (§5) | A bounded agent step drafts the fix (new title/meta/schema/alt text/canonical target), a code step renders a **diff preview** against the live page, and — only once approved — a `cms.write*` tool applies it through the platform's real API. |
| **B — Dispatch to another Karos agent / connector** (`connect`) | `delivery === "existing-product"` | Never a hidden call. This creates a **real, portal-visible job** on the target agent's own Dynamic Agent Studio spec (e.g., a content brief dispatched to the Blog or LinkedIn agent, or a GSC/IndexNow re-indexing request) — same explicit-composition rule RFC-05 §2 and RFC-08 §3 already established for cross-agent calls. If the required connector (e.g., GSC) is not yet connected, the UI's job is to prompt the connect flow (§6), not to silently fall through to guided_manual. |
| **C — Guided kit** (`guided_manual`) | `delivery === "advisory"`, or a machine-appliable fix on a platform we cannot write to (a custom Next.js/Vercel stack, per `fix-recipes.md`'s own "Honest scope": *"Custom stacks get deploy-ready hand-offs"* — already the product's stated policy, not a new one) | Generate the artifact described in §7: a structured, ready-to-hand-to-a-dev-agent spec, plus the task-scoped chat context (§8). |

## 5. Tools needed, and where the real risk is

- New: `cms.detectPlatform` (identify WordPress/Shopify/Webflow/custom from the client's site), `cms.previewFix` (renders the diff for a given `fixAction` without writing anything), `cms.applyFix` (the actual write — WordPress REST, Shopify Admin API, Webflow API; one adapter per platform, same "adapter never infra" rule RFC-06 §6 already established for Branded Shorts), `search.requestIndexing` (GSC/IndexNow ping — the lowest-risk actuator, worth building and shipping first).
- **`cms.applyFix` is the highest-risk tool in this entire migration effort** — it is the only tool in the whole `agent-engine` catalogue so far that writes to a **third party's live production website**, not to Karos's own generated output (contrast with Landing Builder's write-fence, which only ever writes inside our own `OUTPUT_PATH`). It must, at minimum: (a) require the resolved `clientId` + a server-resolved credential, never a client-supplied endpoint or token; (b) refuse to run against anything but a `recId` with a resolved approval record (§3); (c) store the pre-write value before writing, so a single-level rollback is possible (mirroring the snapshot-before-overwrite discipline already used in `register-reputation-agent-v2.ts`); (d) log the write as an auditable event, the same way every other agent in this codebase logs deliverables and activity.
- Reuse: `client.*` for the fact base, RFC-05's `intel.writeReport`-style pattern for the guided-kit artifact.

## 6. Credential storage — this is not a new system, it is two new `platform` values on an existing one

`ClientIntegration` (`karosCMO/src/lib/types.ts`) already models exactly this shape — `{id, clientId, platform, accountName, credentials}` — used today for Instagram/LinkedIn/Google, with tokens **already encrypted at rest** (`src/lib/crypto/token-cipher.ts`, `decryptCredentials` before use) and an existing per-grantor attribution check (`integrationBelongsToCaller`, built for Gmail, directly reusable here). **Do not build a new connector-storage system.** Add `wordpress`/`shopify`/`webflow` as new `platform` values, reuse the encryption and grantor-attribution pattern as-is, and reuse the existing connect-flow UX pattern already live for Google Workspace (RFC-10 §2 covers the portal side of this).

## 7. The guided-kit artifact (bucket 2) — what actually goes in it

For a `guided_manual` recommendation, generate a structured document — call it `AGENT_TASK.md`, written per-client, per-recId — containing: (1) the plain-English `REC_COPY` title/description the client already sees; (2) the underlying technical specifics from the **internal** `VisibilityGap` (evidence, measured value, benchmark) that are deliberately never shown to the client directly (`seo-geo.ts`'s own rule: "INTERNAL — never render raw to a client... Use `recommendations` for the client view") but are exactly what a developer or a dev-agent needs; (3) a ready code/config snippet where the fix type has one (schema JSON-LD, a meta tag block, a robots.txt entry) — genuinely fillable, not a placeholder; (4) an explicit statement of what Karos did and did not do — "we identified this and drafted the fix; we do not have write access to your site to ship it," matching `fix-recipes.md`'s own "Honest scope" language verbatim. This is a bounded agent step (schema-out, Zod-validated per RFC-01 §3), not a tool — the generation itself is a judgment call over already-gathered facts, same tier as RFC-06's graphics-selection step.

## 8. The task-scoped chat — reuse the copilot, do not build a new one

`karosCMO/src/lib/copilot-context.ts` and `copilot-tool-access.ts` already implement a real, security-hardened, role-gated chat system: `buildCopilotSystemPrompt()` assembles per-client context (brand, competitors, jobs, assets) into a system prompt, and `copilot-tool-access.ts` enforces a **client-tool allowlist** (deliberately inverted from a denylist, specifically because a denylist "fails open" — a lesson already learned and written down in that file). **The "Ask AI Architect" idea from the brainstorm should be built as a scoped variant of this existing copilot, not a new component:** call `buildCopilotSystemPrompt()` with an additional, recommendation-specific context block (the `VisibilityGap`'s technical detail from §7, item 2) appended, so the chat is scoped to "help me implement this one fix" rather than the whole account. This reuses the existing role gate (client vs. staff), the existing tool allowlist, and the existing rendering constraints (the chat panel's Markdown-subset rule already documented in `copilot-context.ts`) — all real, hardened work that a new chatbot would otherwise have to re-earn.

## 9. Definition of done

(1) The three actuator paths (§4) are built against the **real** `ActionKind`/`FixAction`/`delivery` fields already in `seo-geo.ts`, not a new taxonomy; (2) `cms.applyFix` never runs without a resolved approval record and a stored pre-write value, closing the exact gap the karos-agents doc's own Finding 1 warns about, before this tool is ever wired to a real client; (3) CMS credentials live on `ClientIntegration` with the existing encryption pattern — no new credential-storage system; (4) the guided-kit artifact and the task-scoped chat both reuse existing infrastructure (§7, §8) rather than duplicating it; (5) the §2 reconciliation question (whether the fuller 75-rec catalog ever merges into the SaaS product) is explicitly raised with whoever owns a3, not silently resolved either way; (6) the lowest-risk actuator (`search.requestIndexing`) ships and is proven on a real client before `cms.applyFix` is attempted on anyone's live site.
