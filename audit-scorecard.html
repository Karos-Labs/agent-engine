P0

allowedTools is never enforced — the ReAct loop can call any registered tool

Architecture
packages/core/src/agent/base-agent.ts:128-133, 209-225 · x-draft-agent.ts:88
Root cause
The tool-lookup path validates existence and input schema but skips the allowlist membership check. allowedTools appears only in the doc comment and the prompt text — advisory to the model, never checked in code. The full merged registry (ledger.writeDeliverable included) is passed as runtime.tools while the draft agent declares only four gate/render tools.
Impact
Research content is serialized verbatim into the next turn's prompt with no trust boundary. An injected instruction in a scraped article (“call ledger.writeDeliverable…”) causes a real ledger write before the human batch-review gate — defeating the entire “nothing persists until a human approves” design. The write-fence only blocks path traversal and cross-tenant fields; a same-tenant write sails through.
Fix
Build the turn schema's tool field as z.enum(config.allowedTools), add a membership check in runOneTurn before the write-fence, and pass only the allowlisted subset of the registry into the loop. Add a regression test — none exists.
P1

Landing gate executes model-authored site code via npm run build

Security
packages/tools/karos-landing/src/gate/gate-tool.ts:147 · write-file-tool.ts:40
Root cause
The gate runs execFileAsync("npm",["run","build"],{cwd:siteRoot,shell:true}) against a tree the LLM wrote. writeSiteFile fences where files land but has no filename allowlist, so next.config.ts/package.json are writable — and Next.js executes them at build time.
Impact
Prompt-injected brand/scrape content steers the make-agent to write a malicious next.config.ts; the gate build runs attacker JS on the host, inheriting ANTHROPIC_API_KEY, GCP ADC and the GCS bucket. Becomes P0 the moment landing-builder deploys alongside credentialed workloads.
Fix
Run the build in an isolated, credential-free, network-restricted sandbox; drop shell:true; deny writes to next.config.*/package*.json.
P1

clientSlug path traversal in landing bundle tools

Security
read-bundle-tool.ts:63 · update-brand-feedback-tool.ts:47 · runs.ts:19
Root cause
Both tools build path.join(bundlesRoot, ctx.clientSlug, …) with the raw slug, unlike siteRootForClient which runs it through sanitizeSegment. Ingress only validates z.string().min(1).
Impact
A run with clientSlug="../../../../etc/attacker" reads and writes JSON outside bundlesRoot — arbitrary-directory read/write scoped only by a caller-supplied string.

Wrap the slug in sanitizeSegment in both tools and add a slug charset regex (/^[a-z0-9][a-z0-9-]*$/) at StartRunRequestSchema so the invariant isn't per-backend.
P1

Security · Tooling
karos-video/src/tools/write-json-file.ts:38 · read-json-file.ts:29 · core/src/agent/write-fence.ts:8

P1

step.code returning undefined crashes real Firestore — tests mask it

Architecture
step-code.ts:36-48 · firestore-store.ts:93 · create-x-agent-workflow.ts:332-337 · fake-firestore.ts:24-27
Root cause
Several code steps (e.g. X step 19 persist-manifest) have no return, so output: undefined is checkpointed. Real Firestore rejects undefined unless ignoreUndefinedProperties is set (it isn't anywhere). The fake store happily stores it, so the whole suite passes.
Impact
On real GCP wiring, every run that survives the human gate crashes at the next void code step — after the deliverable was persisted — and is marked degraded. Affects five of the migrated agents in production only.
Fix
Normalize output ?? null in saveStep (or enable ignoreUndefinedProperties), and make the fake store throw on undefined so tests match production.
P1

No concurrency guard — the same run executes twice in parallel

Architecture · Quality
apps/agent-server/src/routes/runs.ts:82-138 · workflow-engine.ts:58-74
Root cause
Resume never checks status === "awaiting_gate"; run() unconditionally flips to running with no lease/lock (the RFC's Redis lock is unimplemented). POST /start mints a fresh UUID per request.
Impact
Two near-simultaneous approvals (double-click / retried request) both invoke the LLM and re-execute post-gate steps — double model spend and last-write-wins telemetry. A portal retry on start silently creates a second full run.
Fix
Optimistic lease via compare-and-set on status; reject resume of a non-awaiting_gate run with HTTP 409; accept a client idempotency key on start.
P1

Report serializer reports false failures for paused / running runs

Architecture
serialize-run-report.ts:82-85, 139-151 · apps/agent-server/src/report.ts:171-195
Root cause
A missing step record serializes as status:"failed", error:"step did not run", and failedStepId/failedStepIndex are derived from those synthetic failures. The serializer conflates “not reached” with “failed.”
Impact
Every legitimately paused run returns a report claiming failedStepId:"15-batch-review" plus 5–6 more “failed” steps — the portal shows a failed job for a healthy run waiting on a human. Returned in the very response that says awaiting_gate.
Fix
Omit unreached descriptors when status is awaiting_gate/running; never derive failedStepId from synthetic entries (the contract already tolerates a shorter steps array).
P1

Gate-id API asymmetry — round-tripping the returned id 404s

Architecture
step-gate.ts:6-8, 37 · workflow-engine.ts:95-102, 133-140 · runs.ts:101-118
Root cause
The engine returns the qualified pendingGateId (${runId}__${id}) but resolveGate re-qualifies the id it receives — two id namespaces leak across the same boundary in opposite directions.
Impact
A client POSTing back the pendingGateId it was given gets runId__runId__15-batch-review → 404. Both demo and smoke scripts already hardcode the local id as a workaround; the engine asymmetry is unfixed.
Fix
Make resolveGate accept either form (strip a ${runId}__ prefix), or return the local id and keep the qualified id internal. Document one canonical shape in OpenAPI.
P1

Stale pendingGateId / failureReason survive terminal transitions

Architecture
workflow-engine.ts:90 · memory-store.ts:42 · firestore-store.ts:84 · runs.ts:154-159
Root cause
The completion patch is {status, updatedAt, totalCostUsd} and never clears prior fields; merge:true semantics preserve them. GET /status emits pendingGateId whenever defined.
Impact
A resumed-to-completion run still returns {status:"completed", pendingGateId:"…"} — a client polling for pending gates re-surfaces a settled gate forever; a recovered run keeps its old failureReason.
Fix
Clear inapplicable fields on each terminal transition (FieldValue.delete()), or gate pendingGateId on status==="awaiting_gate" in the route.
P1

Budget is dropped on resume and never set by the server

Architecture
workflow-engine.ts:59-84 · runs.ts:69, 122-127 · step-agent.ts:32-37
Root cause
On an existing run, budget comes only from params.budget — the persisted existingRun.budget is ignored; neither start nor resume ever passes one.
Impact
RFC-01's “budget enforced before spend” is structurally present but inert in the deployed server; even a caller who sets it at start loses the ceiling on the post-gate half of the run.
Fix
const budget = params.budget ?? existingRun?.budget threaded into the runtime, plus an env-configurable default per-run ceiling in the route.
P1

App Store capture leg: unguarded fetch/parse wipes sibling legs

Tooling
karos-reputation/src/capture/appstore.ts:39-48, 95-101 · capture-tool.ts:33-55
Root cause
appstorePages calls fetch+JSON.parse with no try/catch, unlike the GBP/Yelp adapters which route every failure through dead().
Impact
A DNS failure or an HTML error page returned with HTTP 200 throws, aborts the sequential leg loop, and turns the entire multi-leg capture into tooling_error — already-captured GBP/Yelp outcomes are discarded and no UNAVAILABLE tombstone is written, violating the three-outcome-per-leg contract.

P1

Triage config NaN hazard hidden behind an as cast

Tooling
karos-reputation/src/triage/schemas.ts:27 · triage-tool.ts:24 · triage.ts:124-125
Root cause
The runtime schema (z.record(string, number)) can't require platform_visibility.default, and an as TriageConfig cast papers over the gap the engine depends on.
Impact
A per-client config override that omits "default" passes validation; every review on an unlisted platform scores value = NaN, so respond-worthy reviews silently route to NO-ACTION. The deterministic routing authority — the one thing that must never be wrong — degrades silently.
Fix

Context for the score

04 What is genuinely strong

The findings above are corrections to an already-high baseline — these controls are real, not aspirational.

✓The layering invariant holds

BaseAgent performs zero direct I/O; Layer 1 makes zero content judgments. The durable-store interface is small enough that the Firestore↔memory swap is real and tested, keeping the Temporal path open.

✓“Model extracts, arithmetic routes”

Zero LLM-decided numbers found anywhere in scope. SEO scoring, reputation triage (a scrupulous banker's-rounding Python port), and intel scoring are pure functions, fixture-locked, with the doctrine gate's arithmetic able to override a model “pass.”

✓Resume-by-replay is elegant & safe

The throw-to-pause gate design with checkpoint short-circuiting is deterministic; scopedStepId designs out sibling-slot checkpoint collisions. Idempotency keys on every commit-phase write.

✓Tests assert side effects, not mocks

Fake only the LLM; run the real engine, real tools, real file store in a temp dir; assert durable outcomes and spy call-counts across simulated crashes. Zero skip/only/todo, zero self-asserting mocks, near-zero any.

✓Every counted constraint verified

11 LinkedIn archetypes, 6 X lanes, 13-field competitor schema, 11-step reputation pulse, 4 doctrine invariants, 600-word blog floor, locked-closed reputation.publish, append-only feedback trail — all present and enforced in code.

✓Honest failure taxonomy

tooling_error never masquerades as a content verdict; UNAVAILABLE is surfaced rather than zero-filled; describeError walks .cause chains; the four-outcome taxonomy was extended with held/blocked_intake end-to-end.
